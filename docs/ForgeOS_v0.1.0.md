# ForgeOS v0.1.0 Development Notes

## The IDT (Interrupt Descriptor Table)

The IDT table was something I was stuck on, not because it was necessarily challenging, but because it was a complex thing to understand. What confused me the most was wondering how one person could possibly write 256 unique interrupt handlers by hand.

My first attempt was actually trying to write vector 0 through vector 255 one by one. I only got to vector 1 before I realized there had to be a better way.

Then I learned about the ISR stub table.

Instead of writing 256 completely different handlers, I made two different macros:

* A macro for exceptions that **do push an error code**.
* A macro for exceptions that **do not push an error code**.

For the exceptions that do not push an error code, I manually push a fake error code so every interrupt reaches the common handler with the same stack layout.

I found the complete exception table on **wiki.osdev.org**, which lists every exception that does and does not automatically push an error code. I assigned each interrupt to the proper macro.

Even though every interrupt has its own entry point, they all eventually jump to one place:

`isr_common_stub`

Right now the common stub simply holds the CPU in a panic state. Later this will become the place where registers are saved and proper exception handling is performed.

# Building the IDT in C

In my C file I defined the `idt_entry` structure.

Each entry has to match Intel's exact layout, so I separated every field using the proper data types.

Each IDT entry contains:

* Offset Low (16 bits)
* Selector (16 bits)
* IST (8 bits)
* Type Attributes (8 bits)
* Offset Mid (16 bits)
* Offset High (32 bits)
* Reserved (32 bits)

After defining the structure, I created:

* An `idt_table` containing 256 IDT entries.
* An `isr_stub_table` containing pointers to every ISR stub generated by NASM.

Then I wrote `idt_set_gate()`.

This function takes two things:

* The interrupt vector.
* The handler address.

The vector is simply the index where that interrupt belongs inside the IDT.

Inside the function I slice the handler address apart so it matches Intel's required IDT format.

After that I use a `for` loop inside `idt_init()` to connect every vector with its corresponding ISR stub.

Finally, I call `idt_init()` from `kernel_main()`.

Once the table is built, I load it into the CPU using `lidt`, enable interrupts with `sti`, and trigger a divide-by-zero exception to test everything.

The divide-by-zero exception successfully jumps into `isr_common_stub`, which is currently my panic handler.

# What Confused Me

One thing that confused me was keeping track of all the different tables.

There was:

* The IDT table.
* The ISR stub table.
* The IDTR descriptor.

Trying to understand what each one did and how they all worked together took me a while.

The more time I spent reading the Intel manuals, looking at diagrams, and running into problems, the more everything started to click.

Eventually I realized:

* The ISR stub table is just an array of function addresses.
* The IDT is what the CPU actually reads.
* The IDTR simply tells the CPU where the IDT lives in memory.

Once I understood those three pieces, the whole design finally made sense.

# The Biggest Bug

One of the biggest problems I ran into had nothing to do with the IDT.

Inside my boot code I had left a placeholder that halted the CPU.

Because of that, execution never transferred control to my `_start` label.

That meant `kernel_main()` never executed.

I spent a long time thinking something was wrong with my interrupt code when the kernel wasn't even reaching it.

The only way I figured this out was by learning how to use **QEMU** together with **GDB**.

Using GDB I stepped through my program instruction by instruction.

Eventually I noticed the CPU always stopped inside the same halt loop:

```
hlt
jmp halt
```

At that point I realized my bootloader was holding the entire program up and never transferring execution to `_start`.

After fixing that, execution finally flowed like this:

```
UEFI
    v 
efi_main
    v
    v 
_start
    v 
kernel_main()
    v 
idt_init()
    v 
lidt
    v 
sti
    v 
divide by zero
    v 
isr_common_stub
```

# Lessons Learned

* Don't try to write 256 interrupt handlers by hand.
* Macros save an incredible amount of work.
* The IDT is just a table that points to handlers.
* The ISR stub table is only used to build the IDT.
* The CPU never reads the ISR stub table directly.
* GDB is one of the most valuable tools when writing an operating system.
* Before assuming a feature is broken, make sure your code is actually executing.
* Sometimes the bug isn't where you think it is.
